# 复盘二模板

阶段二只在用户明确继续后加载。它把复盘一中的候选建议转成真实、可检查的改进，但不会把每一条提案自动视为授权。

## 0. 运行参数

读取并记录：

```text
HUMAN_AGENT_PLAYBOOK_TARGET = <可选的本次覆盖；缺失或空值复用本机保存的默认目标>
```

按 SKILL.md 的首次启动协议调用 `scripts/playbook_settings.py get`，解析安装实例的 `.local/config.json`。首次启动已取得目标就不重复询问；没有保存值也没有当前明确目标时完成首次配置。历史模板或案例里的路径只作候选，不能当成当前默认值选择。当前覆盖不自动改默认值，更换默认值需用户明确指令。不要猜固定路径，也不要把保存仓库 URL 当成远程创建或推送授权。

## 工作流 A：Agent 运行侧

1. 回读复盘一中的 Agent 侧提案和当前限制，检查真实配置和实现，找到直接根因。先分出本轮可实施、已有能力已覆盖、受保护范围待修和证据不足；后两类保留为未实施项，不用“继续”推导解除冻结。
2. 把问题映射到已有规则、项目规则、Skill、脚本、Hook、模型路由、上下文恢复、委派、日志或测试。
3. 优先修复已有能力，不用更长提示词掩盖 Agent 应自主完成的问题。若用户明确授权本会话流程技能化，读取 [流程与自有能力审计](workflow-extraction.md)，审查查重与独立职责，再交ASM make；未经明确授权的候选仍只记录。新技能的验证/安装/交付分别举证，不让能力维护重新接管已移交成果。
4. 多执行单元使用不重叠写集；登记负责人、路径、验证和恢复点。没有隔离收益时由主 Agent 串行完成。
5. 修复后用暴露问题的真实场景做回归，记录命令、输出和局限。
6. 主会话统一验收，检查改动是否真正生效、是否破坏兼容性、是否造成规则膨胀。
7. 用 [经验记录](lesson-record.md) 留下后续观察条件和原场景结果；下一次适用任务回读记录。长期收益未观察时保留 observing，不把当前通过当作持续改善。

写集检查调用：

```bash
python3 scripts/check_write_scope.py --allow /absolute/allowed-repository \
  --protect /absolute/frozen-repository \
  --write /absolute/allowed-repository/document.md
```

路径检查器只读取路径并解析真实位置，不写文件。允许根不构成对其全部内容的修改授权；每个实际文件仍须归属本轮任务。冻结仓库不得作为写集，也不能以“修复复盘发现”为由修改其记录、配置或 Git 状态。受保护范围中的确定性缺陷应给出位置、影响和解除范围后的最小修复；不能把它改写成人类每次都要补充的长提示词。对外部只读素材与写入目标分别判断，不能为限制输出而禁止合法输入。

判断是否存在配置缺陷时，分别核对已保存绑定、当前任务指针与跨设备行为；没有模板内指针不等于没有持久化。区分 CPU 时间与墙钟时间；无可访问原始证据时保留未知，不补造耗时或成本。

每项报告格式：

```text
问题 → 根因 → 修改位置 → 实际修改 → 验证命令/方法 → 证据 → 结果（通过/失败/未验证）→ 风险
```

## 工作流 B：Human–Agent 协作参考手册

使用目标项目现有结构，先读 README、AGENTS、Git 状态和已有目录。手册应成为长期维护的参考书、操作手册、模板库、真实案例库和决策框架，而不是本次任务总结或提示词堆。

以下是手册的长期覆盖方向。本轮只更新与已选提案相关的内容，不要求每次补全所有主题；没有协作改进时报告无手册改动及原因：

- 任务开始前：目标、约束、验收、必须指定与应留给 Agent 的决定；
- 委派：粒度、自主权、能力组合和授权范围；
- 执行中：干预时机、反馈、错误、成本和上下文；
- 多 Agent：职责、依赖、唯一 writer、主会话验收和冲突；
- 验收：证据、复现、回归、范围和不确定性；
- 任务后：即时复盘、反事实、经验筛选和知识沉淀；
- 长期协作：项目知识、任务记忆、SOP、协作契约和持续修订。

每个实用方法尽可能说明适用任务、解决问题、原理、操作步骤、反例、不适用条件和验证方式。真实案例脱敏，并标注事实、推导和待验证建议。把 Agent 工具正确性留在运行侧，避免同一个问题在手册和规则里重复维护。

按本轮证据与手册已有内容去重后选择相关案例，不固定把下列内容重复写入每次手册更新：

- 复盘一与复盘二的人工阅读停点；
- 首次未配置时询问并保存，以后复用本机配置；
- 当前主会话统一验收；
- 不把子 Agent 自报完成当验收；
- 并发改动和其他任务提交的归属；
- 先验收后清理临时资源；
- 双向升级中 Agent 责任和人类责任的分界。

## 跨工作流验收

检查：

- Agent 侧与人类侧职责是否清楚；
- 同一个问题是否重复维护或互相冲突；
- 是否增加了人类负担；
- 方法能否在下一次同类任务复用；
- 关键链接、引用、示例和导航是否有效。

## 环境卫生验收

最终报告必须给出：

- 任务开始前 worktree 数量；
- 本轮创建的 worktree 数量；
- 成功清理数量；
- 残留数量及原因；
- 临时分支、目录、文件和进程状态；
- 本轮创建的终端是否关闭；
- 用户原有工作区是否保持完整。

必须遵守“按需创建 → 登记归属 → 执行 → 安全集成 → 主会话验收 → 自动清理 → 残留核查 → 最终交付”。清理范围只包括本轮创建且明确拥有的资源。无法安全清理时保全成果并如实报告。

## 恢复与交付

执行旧 next 之前回读文件、分支及远端。已有提交和远端相符时不重复交付；完成交付后刷新已有阶段检查点，保留历史失败，不把刷新当作用户收尾或人工批准。

## 最终报告

先回答总目标的交付状态，再分别报告：

1. Agent 侧修复清单和证据；
2. 并行执行记录与集成结果；
3. 手册目标、目录、核心内容和入口；
4. 通过、失败、未验证项目；
5. 未解决问题及风险；
6. 证据支持的改善与待观察效果；
7. 环境卫生验收；
8. Git 提交、推送或明确的授权/技术阻塞。

若阶段二仍有真实人工批准、远程发布、生产操作、凭据或高影响删除边界，停在具体边界，说明已完成的安全部分和需要人类决定的动作。不要用“复盘二已执行”代替业务验收。
