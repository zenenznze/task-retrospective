# 复盘一模板

以下正文用于阶段一审计。它来自多次真实任务的共同结构，必须用当前任务证据填充，不能复制其他任务的结论。

## 任务复盘结论

回答：

- 人类最初要解决的实际问题是什么？
- 显式需求、隐式需求、约束和验收标准分别是什么？
- 目标是否变化？变化来自人类决策、现场事实还是 Agent 误解？
- 哪些结论有直接证据，哪些只是推断，哪些仍待验证？
- 成果最终依据什么证据通过验收？证据覆盖了什么，没有覆盖什么？

## 执行路径审计

按关键决策而非聊天流水账重建：

- 采用了什么路线？为什么？
- 哪些错误、阻塞、误解、返工或无效尝试发生过？
- 哪些决定正确且值得保留？
- 哪些地方只是最终成功，过程并不稳健？
- 哪些等待、重复读取、重复验证、长命令、模型往返或转义失败可以避免？

对成本只报告真实记录。没有运行成本审计时，不估算美元或 token；可以报告可数的调用、等待、返工和时间区间，并标注边界。

## 能力利用审计

### 全局规则

检查相关 AGENTS、引用规则和系统约定：作用、未遵循处、模糊/冲突/重复、过度约束，以及已有规则本来能否防止问题。优先修改已有规则，不因单次事件创建永久全局规则。

### 项目规则

检查项目 AGENTS、README、流程和状态文件：哪些知识应该提前提供，哪些应按需加载，哪些陈旧或重复，哪些项目特殊性不能泛化。

### 已使用 Skills

逐个说明触发时机、输入输出、边界、重复步骤和实际贡献。不要把“加载过”写成“有效执行过”。

### 未使用 Skills 与工具

主动按当前真实目录和可调用能力检索，分成：

- 已存在且明显遗漏；
- 当前可用但本次不适用；
- 当时不可用或无法证明可用；
- 需要新建的能力。

解释为什么没有触发，是发现机制、description、工具组合还是任务边界问题。

### 当前会话流程与自有能力

读取 [流程与自有能力审计](workflow-extraction.md)，重建本Agent自行组织的步骤、判断、脚本、输出和责任转移，不限于调用过的技能。
必须回答“是否值得将本次流程沉淀为技能”，给出reuse/update/create/record_only/do_not_persist、查重、证据、边界、最小验证和授权状态；没有价值时明确不沉淀。阶段一只提案，不因发现候选自行创建。
该结论必须在最后的固定回答中单独列出一项，并保留同样的词表、查重依据和授权状态。

### 模型与执行架构

审计模型路由、思考强度、工具调用、上下文压缩、并行和委派。判断哪些应确定性脚本化、哪些必须串行、哪些并行会增加冲突成本。不要根据模型名猜测实际后端或价格。

## 反事实最优方案

至少给出：

1. 最少步骤路线；
2. 最低模型与工具成本路线；
3. 最高可靠性和可恢复性路线；
4. 值得比较的替代架构及适用条件、收益、代价、风险；
5. 会改变全局执行方式的关键早期发现。

## 人机协作改进

分别回答：

- 人类最初提示词缺了什么，哪些信息其实不应由人类提供？
- Agent 哪些时候应自主查明，哪些时候必须先问？
- 是否存在同一种误解被多次纠正？
- 人类是否过早指定实现，或提供了无关细节？
- 如何写一个只使用任务开始时已知信息的更好初始提示词？

## 能力进化清单

每项改进必须写清：

- 优先级；
- 问题证据；
- 根本原因；
- 准确修改位置；
- 最小修改；
- 预期指标；
- 副作用；
- 验证方法；
- 是否立即实施；
- 归属层级：全局规则、项目规则、Skill、脚本、自动化、知识记录或不沉淀。

特别检查是否可以修改已有能力，避免无意义新建规则和机制。经验条目按
[经验记录](lesson-record.md) 提供适用范围、独立事件与正确案例，给出后续观察条件；
没有证据则保留假设，不把提案当成已生效规则。

## 最后固定回答

单独回答：

1. 本次任务最大的可避免浪费是什么？
2. 本次最值得跨任务复用的经验是什么？
3. 如果只能修改整个 Agent 体系中的一个地方，应该修改哪里，为什么？
4. 能力沉淀决定：从 reuse / update / create / record_only / do_not_persist
   中明确一个，并写出查重依据和授权状态（proposal_only 或 explicit_implementation）。
   没有值得沉淀的候选时也必须显式给出结论，不能省略、也不能只用“以后注意”代替。

第 4 项是独立交付项，不是前面审计段落的重述。字段必须可被脚本解析且不能留空；
推荐用下面的写法（标题可以是 `## 能力沉淀决定`，也可以直接写模板这一项
`4. 能力沉淀决定：<值>`）：

```text
- decision: <reuse | update | create | record_only | do_not_persist>
- 查重：<与该候选可能重叠的已有能力，以及为什么仍要沉淀或为何不要>
- 授权：<proposal_only | explicit_implementation>
```

“查重：”“授权：”后留空、只写“以后注意”，或用否定句（如“不应采用 decision: create”）
代替结论，都不算满足第 4 项。答复交付前先做结构检查：

```bash
python3 scripts/check_phase_one.py --answer <本阶段答复文本文件>
```

它只证明决定值、查重依据和授权状态存在且非空，不判断决定是否合理，
也不构成运行时强制、不证明答复已送达用户；缺失或为空时补齐后再交付。

最后明确：复盘一只形成审计和提案，等待人类阅读，不执行阶段二。
